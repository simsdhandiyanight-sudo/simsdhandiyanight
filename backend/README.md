# Ticketing backend

## Development setup

1. Install Python 3.12 and PostgreSQL.
2. Install dependencies: `python -m pip install -r requirements.txt`
3. Copy the repository `.env.example` to `.env` and configure local values.
4. For a local PostgreSQL database, set `DATABASE_NAME`, `DATABASE_USER`,
   `DATABASE_PASSWORD`, `DATABASE_HOST`, and `DATABASE_PORT`. If
   `DATABASE_NAME` is unset, Django uses a local SQLite database for development
   and tests only.
5. Run `python manage.py migrate`.
6. Run `python manage.py seed_dhandiya_event` to enable backend event APIs,
   ticket registration, payments, and staff operations.
7. Create an administrator with `python manage.py createsuperuser`.
8. Start with `python manage.py runserver`.

The seed command creates the canonical event and its two ticket offers only.
It does not create attendee data, tickets, scans, staff users, or credentials.
Do not use the SQLite development fallback in production.
The public landing and event detail pages display hardcoded event information
without requiring this seed, but online registration and staff operations
remain unavailable until the backend event and ticket offers are created.

### Initial Render administrator

The Render startup command runs `bootstrap_admin` after migrations and event
seeding. Set `BOOTSTRAP_ADMIN_PASSWORD` as a secret in the Render web service
environment before deploying. The configured `BOOTSTRAP_ADMIN_EMAIL` defaults
to `admin@sims.in`. On first startup, the command creates that administrator;
it never changes the password of an existing administrator and refuses to
promote an existing non-admin account. Once Render confirms the first
successful deployment, remove `BOOTSTRAP_ADMIN_PASSWORD` from the service
environment and redeploy to disable future bootstrapping. Do not put the
password in source control or logs.

If the administrator already exists and needs a password reset, set
`BOOTSTRAP_ADMIN_PASSWORD` to the new secret and temporarily set
`BOOTSTRAP_ADMIN_RESET_PASSWORD` to `true` in Render. After confirming the
deployment log reports an updated administrator password, immediately remove
the password secret and reset flag, then redeploy. The flag only resets the
password for the configured email when that account is already an administrator.

## Staff accounts and panel access

Create staff accounts individually in Django admin at `/admin/` using an
administrator account. Scanner accounts may be assigned to a gate through the
Staff assignments section. Scanner staff sign in at `/staff/login` and are
routed to the scanner panel. Registration staff accounts are read-only for
registration lookup. New on-spot registrations are disabled; historical
on-spot registrations and tickets remain available in reports and scanning.
These accounts are not generated by the event seed command.

For local frontend development, copy `client/.env.example` to
`client/.env.local` and set `VITE_API_URL` to the local Django API origin. The
Vite development server proxies `/api` requests to that configured origin; it
does not embed a localhost fallback in the application bundle.

## Render, Neon, and Vercel

The repository-root `render.yaml` defines the Django web service and scheduled
payment-proof maintenance jobs. In Render, create the services from that
Blueprint.
The web service installs the backend requirements, collects static files,
runs database schema migrations and idempotently seeds the canonical event and
ticket tiers at startup, then starts Gunicorn. Disable any previously
activated n8n outbound-email workflows before deploying this change. Keep
`DJANGO_INTERNAL_API_KEY` configured for the Google Sheets sync workflow only;
never expose it in the frontend.

Create a Neon PostgreSQL database and set `DATABASE_URL` on the Render web
service to its TLS-enabled direct connection string. Keep the connection
string in Render's environment, not in source control. Render's worker reuses
that setting from the web service. Use separate Neon databases/branches for
staging and production.

Deploy `client/` as the Vercel project root. Set the build-time
`VITE_API_BASE_URL` to `https://<render-service-host>/api/v1`; it is a public
API URL, not a secret. On Render, set `CORS_ALLOWED_ORIGINS` and
`CSRF_TRUSTED_ORIGINS` to the exact HTTPS Vercel origin, including the
production Vercel hostname. Production Django settings enforce secure cookies
with `SameSite=None` so credentialed API and CSRF requests can cross origins.
Browser privacy settings that block third-party
cookies can prevent session-based staff/admin use across separate Vercel and
Render sites; verify sign-in in the browsers used by event staff.

Set `COLLEGE_TICKET_ID_PREFIX` on the backend only when its default needs to
change. Outbound email delivery has been removed. Issued tickets remain
available through the secure registration page or the ticket download routes;
email delivery history is retained in the database for audit purposes.
Disable any previously activated email workflows in n8n during deployment.
Keep `DJANGO_INTERNAL_API_KEY` private to Render and n8n; never put it in the
frontend or source control.

### Google Sheets ticket register

The PostgreSQL `TicketSheetSync` outbox is authoritative for synchronization
work. After a successful admin approval commits, the backend sends eligible
ticket rows to a locked Google Apps Script Web App for upsert. Configure
`GOOGLE_APPS_SCRIPT_WEBHOOK_URL` with its deployed `/exec` URL and set
`GOOGLE_APPS_SCRIPT_WEBHOOK_SECRET` to the same private secret stored in Apps
Script Script Properties. These values belong on the Render web service only;
never expose them to the frontend or commit the secret. Deployment
instructions and the `Code.gs` implementation are in
`integrations/google-apps-script/README.md`.

The existing `GOOGLE_SHEETS_SPREADSHEET_ID` and
`GOOGLE_SHEETS_SERVICE_ACCOUNT_JSON` settings remain available for the
management-command recovery path. The routine Apps Script webhook uses the
spreadsheet ID stored in Apps Script Script Properties and does not use those
service-account credentials.

Webhook delivery runs after transaction commit, outside payment/ticket row
locks. Transient HTTP or Apps Script write failures receive up to three
immediate attempts. A confirmed response marks the outbox job `SYNCED`;
failures remain visible in Django admin as `FAILED` without changing payment
approval, ticket issuance, or admission status. Django admin → Payments →
Ticket sheet syncs can dispatch selected pending or failed eligible jobs.

There is no always-running retry process: if the web process exits after the
database commit but before its `on_commit` callback runs, the job remains
pending until an administrator dispatches it from that page. This is a
zero-additional-hosting-cost recovery path, not guaranteed background delivery.

The Apps Script creates missing `Online_Tickets` and `OnSpot_Tickets`
worksheets and their exact row-1 schema:

`ticket_id`, `ticket_number`, `registration_id`, `ticket_type`,
`booking_quantity`, `ticket_quantity`, `unit_price`, `name`, `email`, `phone`,
`amount_due`, `payment_method`, `provider_order_id`, `provider_payment_id`,
`upi_id`,
`transaction_id_utr`, `payment_status`, `verified_by`, `verified_at`,
`ticket_status`, `ticket_generated_at`, `email_status`, `email_sent_at`,
`scan_status`, `checked_in_at`, `checked_in_by`, `created_at`, `updated_at`,
`last_synced_at`.

Each row represents one ticket. `booking_quantity` is the number of selected
ticket-tier units, `ticket_quantity` is the number of individual tickets
generated for the booking, `unit_price` is the price of one selected tier unit,
and `amount_due` is the total verified booking amount in INR. Booking-level
values repeat on each ticket row; aggregate booking totals by `registration_id`
to avoid counting a multi-ticket booking more than once. Only tickets linked to
a verified payment and saved QR token are eligible. Rows are upserted by the
stable ticket UUID in `ticket_id`; QR tokens and payment screenshots are never
exported. Apps Script writes current headers to an empty worksheet. It accepts
both the current schema and the known legacy 24-column schema, preserving
legacy headers and order; legacy tabs cannot store
`booking_quantity`, `ticket_quantity`, `unit_price`, `provider_order_id`, or
`provider_payment_id` until separately migrated. Other nonmatching schemas are
rejected without modification. Duplicate ticket IDs or duplicate column
headers remain observable failures rather than being silently discarded.

Cancellation and successful check-in changes requeue the same durable
outbox record. The backfill includes issued, checked-in, and cancelled tickets
with verified payments. `python manage.py backfill_ticket_sheet_syncs`
requeues eligible records and invokes the webhook for each; it can update all
eligible historical tickets, so do not run it in production without explicit
authorization. `process_ticket_sheet_syncs` remains a manual recovery path
using the direct Google Sheets API service-account credentials. No Render
cron is required for the Apps Script webhook.

Payment screenshots are uploaded by the backend using the official Cloudinary
SDK. Set `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, and
`CLOUDINARY_API_SECRET` as secrets on the Render web service; never set these
in the frontend. Proofs are uploaded as `authenticated` image assets under
`college-ticketing/payment-proofs`, not public assets. PostgreSQL stores the
Cloudinary asset identifiers and image metadata. The admin-only screenshot
endpoint proxies Cloudinary's signed authenticated delivery server-side; it
does not send Cloudinary URLs or credentials to the browser. New proof images
are not stored as database binary data.

On startup, `migrate_legacy_payment_proofs` transfers pre-existing binary
proofs to Cloudinary and clears their database binary values. Configure the
Cloudinary credentials before deploying this change if existing manual proof
records need to be retained. The daily Render cleanup cron deletes only
unreferenced authenticated assets at least seven days old. Referenced proofs,
including rejected submissions, are retained for reconciliation and disputes;
apply an explicit retention policy before deleting them.

Online registration uses manual UPI payment proof. The payment QR image is
served by the frontend from `client/public/upi-payment-qr.jpeg`; no UPI ID or
QR URL environment variables are required. Replace that frontend image when
the payment QR changes. Set `PAYMENT_PROOF_RESERVATION_HOURS` (default 24) and
`PAYMENT_PROOF_RESUBMISSION_HOURS` (default 12) to the reservation windows.
Uploaded JPEG/PNG/WebP proof images are capped at 5 MB and stored in the
private Cloudinary assets (not in PostgreSQL or the ephemeral Render
filesystem); only administrators can retrieve them through the authorized
backend proxy. The approval dashboard requires an
administrator to confirm the actual received UTR/amount against bank/UPI
records before approval. The Render expiry cron releases unpaid/rejected
reservations every five minutes.
Applicants submit both the UTR and transaction ID as separate required
references; each is checked against prior manual UPI submissions.

Outbound email sending and new on-spot registration have been removed. Existing
email delivery records and on-spot registrations/tickets remain for historical
audit, reporting, and scanning; no new email delivery jobs are created or sent.
Approved manual-payment tickets can be downloaded from the secure payment-proof
page. College-student tickets remain available through the administrator PDF
download.
College-student tickets can be created individually or imported from CSV in
the administrator ticket tools; each ticket has an independent yearly
sequence and a unique QR token. Existing online and on-spot registrations
remain separate and are not converted into college tickets.

Manual UPI is the only active online payment flow. Before deploying removal of
the retired gateway code, disable its callbacks/webhooks and any externally
configured reconciliation job, then remove its obsolete environment variables
from Render. Historical provider transaction IDs and verification attempts
remain available in the database and payment review dashboard; the application
does not retry those gateway transactions.

Never commit `.env` files. The root `.env.example` contains names and
non-secret development defaults only.
